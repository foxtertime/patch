# kojipatch

Дашборд патчей: для одного или нескольких koji-тегов собирает последние билды
(с учётом наследования тегов), по `extra.source.original_url` определяет
ветку GitLab, с которой собран каждый билд, читает в этой ветке каталог
`PATCH`, классифицирует найденные файлы (CVE / SAST / DAST / other) и строит
самодостаточный HTML-дашборд с вкладкой «Состояние» по каждому тегу и
вкладкой «Изменения», сравнивающей теги между собой.

Дашборд — один HTML-файл без внешних зависимостей: CSS и JS встроены в него,
данные сериализованы в `<script>`, файлом можно поделиться или открыть локально
без веб-сервера.

## Требования

- Python 3.9+
- `koji` — клиент XML-RPC к хабу (нужен только для `collect`/`run`)
- `requests` — HTTP-запросы к GitLab REST v4 (нужен только для `collect`/`run`:
  импортируется лениво внутри транспорта, который дёргает сеть только при
  сборе; `render` работает от готовых снапшотов и его не требует)
- `PyYAML` — разбор конфига

Все модули должны быть доступны в интерпретаторе, которым запускается
`python3 -m kojipatch`; отдельного `requirements.txt` в проекте нет. Поставить
недостающее можно, например, через `pip install koji requests pyyaml` —
пакет `koji` на PyPI и есть официальный клиент проекта Koji.

## Быстрый старт

```bash
export GITLAB_TOKEN=glpat-...                 # опционально, см. «Токен GitLab»
cp kojipatch.example.yaml kojipatch.yaml       # поправить адреса под себя
python3 -m kojipatch --config kojipatch.yaml run --tag os-9.2 -o dashboard.html
```

Сравнить два тега на одной вкладке «Изменения»:

```bash
python3 -m kojipatch --config kojipatch.yaml run \
    --tag os-9.1 --tag os-9.2 -o dashboard.html
```

Собрать снапшоты сейчас, сравнить позже (например, снапшоты разных дат):

```bash
python3 -m kojipatch --config kojipatch.yaml collect --tag os-9.1 -o os-9.1.json
# ... через месяц ...
python3 -m kojipatch --config kojipatch.yaml collect --tag os-9.2 -o os-9.2.json
python3 -m kojipatch render os-9.1.json os-9.2.json -o dashboard.html
```

`--config` можно не передавать флагом, а задать переменной окружения
`KOJIPATCH_CONFIG`.

## Подкоманды

### `collect` — собрать снапшоты в JSON

```bash
python3 -m kojipatch --config kojipatch.yaml collect \
    --tag os-9.1 --tag os-9.2 -o snapshots.json
```

`--tag` можно указывать несколько раз — тогда в выходной файл будет записан
список снапшотов (по одному на тег), которые `render` потом прочитает как
единое целое. Требует `koji.hub` (в конфиге или через `--koji-hub`).

### `render` — построить HTML из уже собранных снапшотов

```bash
python3 -m kojipatch render tests/fixtures/snapshot-os-9.1.json \
    tests/fixtures/snapshot-os-9.2.json -o dashboard.html
```

Принимает один или несколько путей к файлам снапшотов (каждый файл может
содержать как один снапшот, так и список — как из `collect` с несколькими
`--tag`); все они объединяются и передаются на рендер вместе, в порядке
перечисления файлов и снапшотов внутри них. `koji.hub` в конфиге для этой
команды не нужен — `render` работает только из данных снапшота, к koji и
GitLab не обращается и конфиг вообще не обязателен: команда выше отработала
без флага `--config`.

### `run` — собрать и сразу отрендерить одним прогоном

```bash
python3 -m kojipatch --config kojipatch.yaml run --tag os-9.1 --tag os-9.2 \
    -o dashboard.html --save-snapshots snapshots.json
```

Эквивалент `collect` + `render` за один вызов; `--save-snapshots` попутно
сохраняет собранные снапшоты в JSON (необязательно).

### Общие флаги (перед именем подкоманды)

| Флаг | Что делает |
|---|---|
| `--config PATH` | путь к YAML-конфигу (или `KOJIPATCH_CONFIG` в окружении) |
| `--koji-hub URL` | перекрыть `koji.hub` из конфига |
| `--gitlab-api URL` | перекрыть адрес GitLab API (пишется как хост `default_host` или `*`, если `default_host` не задан) |
| `--patch-dir NAME` | перекрыть имя каталога патчей (по умолчанию `PATCH`) |
| `--jobs N` | параллельных запросов к GitLab при сборе, по умолчанию 8 |
| `--max-problems N` | см. «Коды возврата» — учитывается только для `collect`/`run` |
| `--log-level {error,warning,info,debug}` | подробность лога, по умолчанию `info`; см. «Логи» |

Эти флаги общие для всего CLI и должны идти **до** имени подкоманды
(`kojipatch --log-level debug run --tag ...`, а не
`kojipatch run --log-level debug --tag ...`) — таковы правила
`argparse`-подпарсеров, используемых в проекте.

## Конфигурация

Конфиг — YAML-файл, пример в `kojipatch.example.yaml`. Все ключи, кроме
`koji.hub` (для `collect`/`run`) и `gitlab.hosts.<host>.api` (для каждого
описанного хоста), необязательны.

| Ключ | Обязателен | По умолчанию | Что делает |
|---|---|---|---|
| `koji.hub` | да для `collect`/`run`, не нужен для `render` | — | XML-RPC адрес хаба; можно перекрыть `--koji-hub` |
| `koji.web` | нет | нет ссылок на koji в дашборде | база для ссылок вида `/search?match=exact&type=build&terms=NVR` |
| `gitlab.default_host` | нет | — | хост, на который будет отправлен запрос, если хост из `original_url` не описан в `gitlab.hosts` |
| `gitlab.token_env` | нет | `GITLAB_TOKEN` | имя переменной окружения, из которой читается токен GitLab |
| `gitlab.hosts.<host>.api` | да для каждого описанного хоста | — | база REST v4, например `https://gitlab.example.com/api/v4` |
| `gitlab.hosts.<host>.web` | нет | `api` до `/api/...` | база для веб-ссылок на дерево и файлы репозитория |
| `patch_dir` | нет | `PATCH` | имя каталога патчей в корне репозитория; можно перекрыть `--patch-dir` |
| `patch_classes` | нет | правила для CVE, SAST, DAST + `other: '.*'` | список правил `{name, pattern}` — регулярка по имени файла патча → класс |

Правила `patch_classes` применяются по порядку, побеждает первое совпадение
(`re.search`, без привязки к началу строки). По умолчанию CVE опознаётся по
идентификатору в любом месте имени (`httpd-2.4.62-cve-2024-42516.patch.new`),
а SAST и DAST — по вхождению маркера, тоже в любом месте
(`SAST-src.core.ngx_file.c.patch.new` и `httpd-2.4.62-sast-src.core.c.patch.new`
оба попадут в SAST). Имя, где есть и CVE-идентификатор, и маркер SAST, уйдёт в
CVE: правило CVE стоит первым. Расширение роли не играет — классифицируется всё
имя файла целиком, так что `.patch`, `.patch.new` и любое другое равнозначны.
Если понадобится строже, чтобы маркер не ловился внутри слова, замените правило
на `'(?i)(?:^|[^a-z0-9])sast(?:[^a-z0-9]|$)'`. Если последнее правило не
всеохватное, к списку автоматически добавляется `other: '.*'`, так что любой
файл в каталоге патчей всегда получает класс. Разделы `koji`, `gitlab` и
`gitlab.hosts.<host>` при разборе проверяются на форму: если вместо
отображения (`{...}`) там оказалась строка или список, `load_config`
поднимает `ConfigError` с понятным сообщением, а не падает трейсбеком.

### Токен GitLab

Токен читается только из переменной окружения (имя задаётся `gitlab.token_env`,
по умолчанию `GITLAB_TOKEN`) — специального флага для него нет, чтобы он не
попадал в историю шелла и в список процессов:

```bash
export GITLAB_TOKEN=glpat-...
```

Токен опционален. Без него запросы к GitLab идут анонимно — рабочий режим
для публичных репозиториев; для приватных `401`/`403` в ответ на запрос
дерева `PATCH` не роняют весь прогон, а записываются в `problems`
конкретного билда (см. «Формат снапшота»), и такой билд помечается в
дашборде тегом `gitlab-error`.

## Дашборд

### Вкладка «Состояние»

Отвечает на вопрос «что сейчас в теге»: карточки-счётчики (всего билдов,
с патчами, без патчей, проблемных, отдельно по каждому классу патчей) и
таблица билдов с раскрытием строки — ссылки на Koji и GitLab, патчи по
классам (со ссылками на файл), пакеты блоками по архитектуре, проблемы.

### Вкладка «Изменения»

Появляется, только когда на вход подано два и более снапшота. Есть
переключатель переходов: последовательные пары `T1→T2`, `T2→T3`, … и, если
снапшотов больше двух, ещё и сводный переход `T1→Tn`. Показываются десять
карточек-счётчиков диффа: агрегат «изменились» (версия, патчи, состав RPM
или ветка — что угодно из перечисленного ниже), «появились» (`added`),
«исчезли» (`removed`), «версия выросла» (`upgraded`), «версия упала»
(`downgraded`), «версия та же» (`unchanged` — но патчи или RPM могли
измениться и тогда), «патчи пришли» (`patches+`), «патчи ушли» (`patches-`),
«состав RPM» (`repackaged`), «сменили ветку» (`branch-changed`). Ниже —
таблица изменившихся компонентов с раскрытием «было / стало».

Списки RPM в раскрытии разбиты на блоки по архитектуре (`src`, `noarch`,
дальше остальные по алфавиту) и выровнены построчно: один подпакет
занимает одну строку в обеих колонках, поэтому версии сравниваются по
горизонтали. Подпакет сопоставляется по `name.arch`, без version-release,
— иначе обновление билда выглядело бы как полная замена состава.
Пропавший подпакет остаётся на своём месте, напротив него пустая ячейка;
пришедший уходит вниз своего блока, чтобы не сдвигать строки выше. Счётчик
в заголовке блока считает свою сторону, так что у исчезнувшей целиком
архитектуры он показывает 0.

### Теги строк

Вычисляемые метки поверх строки, к koji-тегам отношения не имеют.

На вкладке «Состояние»: `cve`, `sast`, `dast`, `other` (класс патча,
присутствует в билде хотя бы один патч этого класса), `no-patch` (у ветки
нет каталога `PATCH`, т.е. `patch_dir_present == false`), `no-source`
(в билде нет `extra.source.original_url`), `from-commit` (билд собран не с
ветки, а прямо с коммита — источник это допускает, но диффа веток тогда не
будет), `gitlab-error` (репозиторий, ветка или каталог патчей недоступны —
включает и `bad source url`, и любой `gitlab: ...`, включая `401`/`403` без
токена), `internal-error` (сбор данных по билду упал с неожиданной
исключительной ситуацией — сама ошибка не роняет весь прогон, а
записывается в `problems` билда).

На вкладке «Изменения»: `added`, `removed`, `unchanged`, `upgraded`,
`downgraded` (статус компонента) и, если применимо, `patches+`, `patches-`,
`repackaged` (изменился список RPM без смены EVR), `branch-changed`.

### Фильтры, поиск, ссылка на срез

Клик по карточке-счётчику или по тегу строки ставит фильтр; несколько
фильтров на одной вкладке складываются по И, повторный клик снимает фильтр.
Поле поиска ищет по имени компонента, NVR, ветке, именам файлов патчей,
CVE-ID и именам RPM. Текущий вид — активная вкладка, выбранный тег
(«Состояние») или переход («Изменения»), фильтры, поисковый запрос,
сортировка — синхронизируется с `location.hash`, поэтому ссылку на
конкретный срез дашборда можно скопировать и переслать: при открытии такой
ссылки состояние восстанавливается из хеша.

## Логи

Всё логирование настраивается одним общим флагом `--log-level`
(`error`/`warning`/`info`/`debug`, по умолчанию `info`) и идёт в stderr:

| Уровень | Что в нём видно |
|---|---|
| `error` | только фатальные ошибки — та самая одна строка перед кодом возврата 2 |
| `warning` | плюс проблемы отдельных билдов (то, что попадает в `problems` снапшота и тег `gitlab-error`/`internal-error` в дашборде), повторы запросов к GitLab после `429`/`5xx`, отсутствие `multicall` на старом хабе koji (сбор идёт последовательными вызовами вместо пакетных), превышение `--max-problems` |
| `info` (по умолчанию) | плюс параметры прогона (хаб, теги, `--jobs`, задан ли токен), размер тега, прогресс сбора примерно на каждые 5% билдов, итоговая сводка по тегу, имя записанного файла, общее время |
| `debug` | плюс каждый запрос к GitLab (URL, код ответа, длительность, тело ответа при ошибке) и каждый вызов koji (метод, число билдов в пакете, длительность — у XML-RPC своих URL и кода ответа нет), попадания в кэш дерева патчей, полный traceback фатальной ошибки |

Пример строки в обычном формате (`info` и выше):

```
23:08:22 INFO    cli: написан dashboard.html
```

На `debug` формат тот же, но с именем потока — при `--jobs` больше единицы
сбор идёт в пуле потоков, и без имени в строке не разобрать, какой запрос
к какому потоку относится:

```
23:08:53 DEBUG   [w_0] gitlab: GET https://gitlab.example.com/api/v4/projects/g%2Fpkg1/repository/tree ref=br path=PATCH → 200 за 0.00 с
```

Логи всегда идут в stderr, а не в stdout, поэтому `-o` (файл дашборда или
снапшота) и `2>run.log` (файл журнала) друг другу не мешают:

```bash
python3 -m kojipatch --config kojipatch.yaml --log-level debug run \
    --tag os-9.2 -o dashboard.html 2>run.log
```

`--log-level debug` на теге в несколько сотен билдов даёт тысячи строк — это
ожидаемо, уровень для разбора конкретной проблемы (например, почему билд
получил `gitlab-error`), а не для повседневного запуска.

Токен GitLab (см. раздел выше) ни на одном уровне, включая `debug`, в лог
не попадает: в строку параметров прогона пишется только `задан`/`не задан`,
а из параметров HTTP-запроса в лог уходят `ref`/`path`/`page`, но не
заголовки.

## Коды возврата

| Код | Когда |
|---|---|
| 0 | успех |
| 1 | только для `collect`/`run`: суммарно по всем собранным в этом прогоне снапшотам проблемных билдов больше, чем `--max-problems` |
| 2 | фатальная ошибка: конфиг не читается или не проходит валидацию, koji недоступен на уровне транспорта, снапшот не разбирается, шаблон дашборда не найден, ошибка ввода-вывода и т. п. |

`--max-problems` без значения (флаг не передан) отключает проверку и код 1
не возвращается никогда. Проверка выполняется только после `collect`/`run` —
`render` возвращает 0 сразу после успешной записи файла и не считает
проблемы в загруженных снапшотах, даже если `--max-problems` передан.

Во всех случаях кода 2 пользователю на уровне `error` печатается одна строка
вида `<описание>: <исключение>` — конфиг ли не читается, не разбирается ли
снапшот или шаблон, ошибка ли это ввода-вывода, или что-то совсем
непредвиденное (koji недоступен на уровне транспорта и т. п.). Полный
traceback этой же ошибки печатается дополнительно, но только на
`--log-level debug` — см. «Логи».

## Формат снапшота

Файл, который пишет `collect` (или `run --save-snapshots`) и читает
`render`, — JSON-массив снапшотов (или один объект снапшота — обе формы
понимает `render`). Пример на одном билде:

```json
[
 {
  "schema": 1,
  "tag": "os-9.1",
  "generated": "2026-07-01T00:00:00+03:00",
  "koji_hub": "https://hub/kojihub",
  "koji_web": "https://hub/koji",
  "builds": [
   {
    "nvr": "nginx-1.24.0-1.el9",
    "name": "nginx",
    "version": "1.24.0",
    "release": "1.el9",
    "epoch": null,
    "build_id": 1,
    "task_id": 2,
    "owner": "builder",
    "completed": "2026-05-14",
    "source": {
     "raw": "git+ssh://git@h/g/nginx?#origin/main",
     "host": "h",
     "project": "g/nginx",
     "ref": "main",
     "ref_kind": "branch",
     "web_url": "https://gl/tree"
    },
    "patch_dir_present": true,
    "patches": [
     {
      "path": "PATCH/CVE-2024-7347.patch",
      "name": "CVE-2024-7347.patch",
      "class": "CVE",
      "cves": ["CVE-2024-7347"],
      "web_url": "https://gl/blob/CVE-2024-7347.patch"
     }
    ],
    "rpms": ["nginx-1.24.0-1.el9.x86_64"],
    "problems": []
   }
  ]
 }
]
```

`schema` — версия формата (сейчас `1`); `render` откажется читать файл с
другим значением. `koji_hub`/`koji_web` снапшота — не текущий конфиг, а то,
чем реально пользовался `collect` в момент сбора этого конкретного снапшота.
`render` использует `koji_web` по-разному на двух вкладках: на «Состоянии»
каждая строка берёт `koji_web` **своего** снапшота (если теги собраны с
разных хабов, ссылки у них тоже будут на разные хабы), а на «Изменениях» все
пары строятся с `koji_web` **первого** переданного снапшота — даже для строк,
которые целиком относятся к более позднему тегу.

`patch_dir_present` трёхзначен:
- `true` — каталог `PATCH` в ветке прочитан (список файлов, пусть и пустой,
  получен);
- `false` — ветка существует, но каталога `PATCH` в ней нет;
- `null` — определить не удалось: либо у билда вовсе нет источника или ссылка
  на него не разбирается, либо GitLab ответил ошибкой. Причина в этом случае
  всегда есть в `problems`.

`false` и `null` в этом случае клиент различает вторым запросом. Ответ `404`
на запрос дерева `PATCH` сам по себе неоднозначен: так отвечает и «в ветке
нет каталога `PATCH`», и «ветки уже нет», причём формулировка зависит от
версии GitLab — встречаются `404 Tree Not Found`, `404 invalid revision or
path Not Found`, причина в поле `error` вместо `message` и вовсе пустое тело.
Поэтому решает не текст ответа: любой `404`, кроме явного `404 Project Not
Found`, уточняется запросом `GET /repository/commits/<ref>`. Если коммит
найден — ветка существует, каталога нет, `patch_dir_present = false` и никакой
проблемы не записывается. Если и там `404` — `problems: ["gitlab: ref not
found"]` и `patch_dir_present = null`, а не молчаливое «патчей нет».
`404 Project Not Found` распознаётся сразу и второго запроса не вызывает.

`problems` — список текстовых причин, с которыми накопитель столкнулся по
конкретному билду; префиксы значимы и определяют теги в дашборде (см. выше):
`no source url`, `bad source url: ...`, `gitlab: ...` (в том числе
`gitlab: no ref in source url`, `gitlab: unknown host`,
`gitlab: ref not found`, `gitlab: 401 ...`/`gitlab: 403 ...` без валидного
токена), `internal error: ...`.

```bash
python3 -m unittest discover -s tests -v
```
